# 05 样本与表关系规则

## 1. 分析主表

订单级主表以 `order_id` 为唯一键，从每个订单唯一一条
`is_courier_grabbed = 1` 的成功运单构造。

原始运单表不是一行一个订单，而是一行一次派单形成的运单：骑手拒绝后，订单会重新进入派单系统并生成新的 `waybill_id`。因此：

- 成功运单用于计算最终履约结果；
- 所有运单用于统计派单尝试次数、拒绝次数和首次派单时间；
- `platform_order_time` 和 `order_push_time` 在少量多运单订单中会随尝试变化，订单级流入时间取所有尝试中的最早正值，同时保留成功运单本身的时间字段供审计；
- 禁止直接按原始运单行数计算订单量或超时率。

## 2. 样本分层

### 2.1 `is_valid_completed`

订单有有效预计送达时间和实际送达时间，并且下单、首次进入配送、接单、取餐、送达的核心时间链路无倒置。单个派单过程字段缺失不会自动删除一个结果完整的订单，而是通过独立的调度时间有效标记控制相关阶段分析。

用途：准时率、超时分钟数、履约阶段时长等结果分析的统一分母。

### 2.2 `is_on_demand`

`is_prebook = 0`。

用途：高峰期即时需求和运力配置的主分析样本。预订单不删除，单独保留用于对照，因为其下单至进入配送系统的等待机制与即时单不同。

### 2.3 `is_known_da`

`da_id != 0`。

用途：商圈排名和商圈运力建议。`da_id = 0` 的订单仍纳入全城总体指标，但不能强行分配给某个已知商圈。

### 2.4 `is_strategy_eligible`

同时满足：有效完成、即时单、商圈已知。

用途：商圈 × 时间段诊断和历史运力配置回放。

## 3. 日期和时间口径

- `dt` 作为官方业务日期保留，跨午夜完成的订单仍归属原始业务日期；
- 订单流入时间使用 `order_push_time`，因为它表示订单进入配送系统；
- 时间戳由 Unix 秒转换为 Asia/Shanghai 本地时间；
- 策略初始粒度为 `da_id × dt × 30分钟订单流入时间段`，之后再按单元样本量决定是否合并为 60 分钟。

## 4. 超时口径

```text
is_late = arrive_time > estimate_arrived_time
late_minutes = max(0, arrive_time - estimate_arrived_time) / 60
```

分析性严重程度分层：

- `on_time`：不晚于 ETA；
- `late_0_10m`：超时大于 0 且不超过 10 分钟；
- `late_10_30m`：超时大于 10 且不超过 30 分钟；
- `late_30m_plus`：超时大于 30 分钟。

以上阈值仅作为本分析的严重程度分层，不对应平台官方 SLA。

## 5. 调度快照关系

- `dispatch_waybill`：某决策时点等待分配的订单集合；
- `dispatch_rider`：同一决策时点的候选骑手集合；
- 可按 `dt + dispatch_time` 聚合供需数量，或进一步做空间网格聚合；
- 不可仅按 `dispatch_time` 做订单—骑手逐行连接并解释成实际匹配。

## 6. 可观测边界

- `grab_time -> fetch_time` 是接单至取餐时长，同时包含骑手到店路程和可能的到店等待，不能直接归因于商家备餐；
- 脱敏经纬度仅用于相对空间距离和网格分析，不代表真实地址；
- 8 天数据可支持短周期横截面诊断与跨期留出验证，不支持季节性或全年经营趋势结论；
- 历史回放输出是条件假设下的估计，不等于策略上线后的因果效果。
